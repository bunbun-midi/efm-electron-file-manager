# Electron File Manager

A cross-platform (Mac-first) file manager built on ElectronJS, with its own
internal Windows-98-style windowing system, a freely-rearrangeable icon view,
full-viewport image previews, a real in-app terminal, and a small scripting
API for "virtual directories" — folders whose contents are generated by code
instead of read from disk.

## Running it

```bash
npm install
npm start
```

Requires Node.js, a native build toolchain (Python 3, `make`, a C/C++
compiler — Xcode Command Line Tools on macOS, `build-essential` on Linux,
"Desktop development with C++" on Windows), and enough disk space for the
Electron download. The build toolchain is only needed because the terminal
feature depends on `node-pty`, a native module; `npm install` automatically
rebuilds it for Electron via a `postinstall` script (`@electron/rebuild`).
If that step fails, the rest of the app still runs fine — only the terminal
feature degrades, with a clear in-app error explaining why. See **"Setting
up the terminal feature"** below if you hit trouble there.

Tested target: macOS, but it uses no Mac-only APIs and should run on
Windows/Linux too.

## Setting up the terminal feature

The terminal is built on `node-pty` (a native module giving a real
pseudo-terminal — the same approach VS Code, Hyper, and most other
Electron-based terminals use, and meaningfully better than just piping a
plain subprocess: interactive programs check whether they're attached to a
real TTY and behave differently if not, so `vim`, `less`, colored `ls`, and
Ctrl+C job control all need this to work correctly) plus
[xterm.js](https://xtermjs.org) to render it.

Native modules need to be compiled specifically for Electron's own Node/V8
ABI, not just plain Node — `npm install`'s `postinstall` step runs
`@electron/rebuild` automatically to do this. If it fails:

```bash
npx electron-rebuild -f -w node-pty
```

Common causes: no C/C++ build toolchain installed (see the requirements in
"Running it" above), or a network hiccup fetching Electron's headers. If
`node-pty` still won't load, the rest of the app is completely unaffected —
opening a terminal just shows a clear in-app error instead of a crash.

**Where things live**, if you're debugging this: `main.js`'s `terminal:*`
IPC handlers own the actual `node-pty` process (spawn/write/resize/kill,
one per terminal window, cleaned up on window close and app quit) and push
its output to the renderer via `terminal:data`/`terminal:exit` events;
`preload.js` exposes thin wrappers over those; `src/terminalWindow.js` is
the window itself (chrome matching the rest of the app, an xterm.js
instance wired to those wrappers, a `ResizeObserver` keeping the pty's
dimensions in sync with the window's actual size); `src/terminalSettings.js`
is the shared, persisted appearance profile and its settings modal;
`src/vendor/xterm/` is xterm.js and its fit addon, vendored as their
prebuilt browser bundles (MIT-licensed, LICENSE files included) since this
project deliberately has no build step to bundle them otherwise.

## Feature guide

**Settings JSON and shortcut help:** Settings → **Export JSON** writes the
current general/window-appearance form as a versioned JSON file. **Import JSON**
validates a JSON file and loads a draft; review it and click Save, or Cancel to
discard it. These files contain the Settings-dialog options, not bookmarks,
file metadata, terminal profiles, or desktop shortcut definitions. Desktop image
paths remain local paths. Help → **Shortcuts** opens a small-font, nonmodal,
draggable/resizable reference. **Alt+E** and **Command+E** open a Home window;
**Alt+Q** remains the titlebar-menu shortcut. Ctrl+E still opens folder search.

**Desktop icons:** Trash/Recycle Bin, Favorites (images), and Favorites (files
and folders) appear automatically. Favorites open `vdir://favorites` and
`vdir://favorites_`; Trash/Recycle Bin opens the OS location. Each desktop icon
or shortcut has an **Appearance** context-menu command, with its own font,
text size/color, background color/opacity, and optional icon image. The image
is embedded in the shortcut settings, so the original may subsequently move.
The image chooser accepts browser-supported image formats (including SVG and
ICO); unsupported images are rejected after a decode check. Files are limited
to 8 MB each. The 3×3 grid selects a label anchor, with inside/outside placement
and left/center text alignment. Center always overlays the icon. Label placement
tracks actual image dimensions and text size as the icon changes size.

Drop one or several files onto an application/script desktop shortcut to launch
it with those paths, without moving the files. Windows EXE/COM launches use
separate arguments; BAT/CMD launches preserve literal path characters with
delayed expansion disabled. PowerShell scripts use the existing execution policy.
macOS `.app` targets receive documents through `open -a`; shell scripts use the
corresponding shell, and native executables launch directly. Shell-script drops
on Windows require that shell to already be installed. Scripts launch in the
background, not in the app's terminal. Windows argument passing is tested;
macOS behavior has not been exercised on this Windows development machine.

Chromium's disposable session/cache files now use a unique temporary directory
per app process, separate from `userData`. This avoids competing instances
sharing a locked cache and leaves existing saved settings untouched. It does
not alter permissions or delete old cache directories.

**Window appearance settings:** File → Settings now has a draggable Settings
titlebar and two independently scrolling columns. General controls stay on the
left; the compact Window appearance column on the right groups frame/bevel/
shadow colors and sizes, active/inactive titlebars, buttons, inputs, address and
status bars, folder backgrounds and borders, scrollbars, detail rows/headers,
resize handles, context menus, and the titlebar system menu. Expand a group to
edit its controls. Colors and sizes preview live without rebuilding folder
contents. Each column has its own Defaults button; Save persists both sections,
while Cancel, Escape, or closing the dialog discards appearance previews.
Existing titlebar color preferences are migrated to the new gradient controls.
The definitions and validation live in `src/windowAppearance.js`, with the
window drawing rules in `src/windowAppearance.css`.

Context-menu rows default to 2 px vertical padding instead of 5 px; this is also
adjustable in Window appearance. Menus are constrained to the viewport. Enter
in an inline rename field commits the name and does not open the file.

**Transfers, annotations, and bookmarks:** Plain dragging between folder windows
or onto a folder moves the selection; hold **Ctrl** to copy. Ctrl+C / Ctrl+V
(Cmd+C / Cmd+V on macOS) copies one or several files/folders recursively.
Ctrl+X cuts instead. Text fields retain their normal text clipboard behavior.
Collisions get a unique name instead of replacing an existing item. Failed cut
items remain on the app clipboard for retry, and errors remain in the status bar.
Alt+drop on the desktop continues to create a desktop shortcut.

Detail view now also includes **PrevName**, **OrigName**, **#**, **Note**, **MD5**,
**SHA256**, and **SHA512**. An in-app rename records the immediately preceding
name and keeps the name before the first rename as OrigName. Click a # or Note
cell to edit it; Enter or leaving the field saves, Escape cancels. # accepts
letters, digits, and spaces. Both fields sort naturally (A2 before A10), support
ascending/descending order, and allow duplicates. Hashes are streamed only when
you choose **Calculate MD5/SHA256/SHA512** from a file's context menu, including
selected groups of files. Folders have no implicit aggregate hash. Settings →
**Show Hash Calc in Context Menu** controls those commands. Saved hashes are
hidden on a subsequent listing if file size or modification time has changed.

Choose **Favorite** on a real file or folder to bookmark it in
**vdir://favorites_**, available from the virtual directories root. **Unfavorite**
removes the bookmark. This is separate from the image viewer's existing
**vdir://favorites** collection. Favorites have a persistent border in both
views; Settings → **Favorite highlight color** controls its color (aqua by
default), separately from search highlighting. A Favorite command applies to
the selection when invoked on a selected item. Bookmarks follow in-app moves
and renames; copied items do not automatically become favorites.

Annotations, hashes, bookmarks, and original creation dates are saved in
`entry-metadata.json` in Electron's user-data folder. Metadata follows in-app
moves, copies, and renames, including descendants of a transferred folder.
Filesystem modification timestamps are preserved on copies. On Windows, the
app also restores native creation timestamps using the
[Windows file/directory creation-time APIs](https://learn.microsoft.com/en-us/dotnet/api/system.io.directory.setcreationtimeutc).
If that is unavailable (including on macOS/Linux), the original creation date
is still retained and displayed by this app. External moves/renames are not
tracked, and the metadata store is local to this app installation. Metadata is
not written into the files themselves.

**Native Properties:** Select a file or folder and press **Alt+Enter**, or
choose **Properties** from its context menu, to open Windows Properties or
macOS Finder Get Info. Desktop shortcuts also offer Properties for their
target. Real files referenced by virtual directories support Properties;
purely generated items have no corresponding native file, so the command
is disabled. macOS may request permission to control Finder; that platform
integration has not been tested here. Linux Properties is not yet supported.
Windows uses the native [SHObjectProperties API](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shobjectproperties)
through a small helper without additional libraries.
Image icons stay attached while being raised on click, preserving native
double-click detection and opening the internal viewer as usual.

1. **Detail view + icon view.** Every window has both. Detail view is a
   sortable table — click a column header to sort, drag the edge between
   two headers to resize that column (widths are kept per-window for the
   session). Standard columns: Name, Kind, Size, Date Created, Date Modified,
   plus the metadata columns described above. Icon
   view lays everything out on an initial grid, but every icon can be
   dragged anywhere — positions are saved per-directory (`layout:get/set`
   IPC, persisted to a JSON file in Electron's `userData` folder) so your
   arrangement survives reopening the folder. Moving one icon only ever
   affects that icon — each icon's default grid slot is tied to its own
   place in the listing, not a counter shared with the others, so dragging
   one out of the grid leaves a gap instead of the rest sliding over to
   "fill in" for it.
   In detail view, right-click a folder and choose **Calc Folder Size** to
   total the file bytes in it and its subfolders, including hidden files.
   The existing Size column displays the result, also on subsequent visits
   and after restarting the app. Values are saved in `folder-sizes.json`
   in Electron's user-data directory and represent the last calculation,
   not a live filesystem monitor. Choose the command again to refresh;
   hover over the size for exact bytes and its calculation time. Unreadable
   descendants produce a clearly marked partial total. Symbolic links and
   junctions are excluded to avoid cycles and counting outside the folder.
   Synthetic virtual folders have no on-disk size; virtual entries backed
   by a real folder support calculation. Size sorting uses saved totals.
   Every column, including the last, can be resized from its right edge;
   other widths stay fixed and the table scrolls horizontally when needed.
2. **Colored-square selection points.** Every file/folder is represented by a
   small colored square (color is derived from the file extension, so e.g.
   all `.txt` files share a color, unless you've overridden it — right-click
   any file and choose **Change Icon Color…** to set one just for that
   extension, or **Reset Icon Color** to go back to the default; this is a
   global preference, so it applies everywhere that extension shows up).
   In icon view, the filename label is visually anchored to the square's
   lower-right corner. Selecting an item highlights the square with a blue
   outline and the label with a solid highlight, so the current selection
   is always obvious. Arrow keys in icon view move the selection to
   whichever icon is actually nearest on screen in that direction — not
   just the next one in list order — so navigation still makes sense after
   you've dragged icons around freely. In either view, just start typing to
   jump to the first item whose name starts with what you typed
   (Windows-Explorer-style type-ahead) — keep typing to narrow it further,
   or tap the same letter repeatedly to cycle through everything starting
   with it.
   **File → Settings → Use file/folder icons** can replace these color blocks
   with the operating system's associated file/folder icons, including icons
   embedded in Windows executables. Folders use the supplied custom SVG
   artwork (`src/assets/folder.svg`), including virtual folders. This applies to icon/detail views, search results, and desktop
   shortcuts. Image thumbnails still take precedence in icon view. Virtual
   entries without a real path and unavailable native icons retain their
   colored fallback. The preference persists and switches existing icons in
   place without resetting folder viewports.
3. **Image thumbnails and per-icon sizing.** Image files (`.png .apng .jpg
   .jpeg .jpe .jfif .gif .bmp .webp .svg .ico .tif .tiff .avif`) show
   aspect-preserving thumbnails in icon view and on desktop shortcuts,
   using Electron's built-in image decoder. Unsupported files (including
   TIFF on Chromium versions that cannot decode it), missing files, and
   corrupt images retain their colored icon. No image libraries are added.

   Hover over any icon or its label and hold **Ctrl** while scrolling:
   wheel-up enlarges that icon; wheel-down shrinks it, smoothly between
   **16 and 3840 pixels**. Its top-left anchor stays in place and surrounding
   icons are not rearranged. Individual sizes override Settings' default
   icon size; icons without an override continue to follow Settings.
   For thumbnails, size means the longest image side: portrait and landscape
   icons have rectangular hit areas and selection outlines matching their
   image dimensions. Empty square padding does not intercept clicks or
   marquee selection. Image icons have no left/top inset, so they can be
   placed against the folder's left edge; their name labels remain clickable.

   **Alt+click an image icon** toggles between the browser's **default**
   scaling and explicit **bilinear** filtering. The hover tooltip identifies
   the current mode. Default mode retains native image animation; bilinear
   mode uses a still thumbnail, redrawn at the current size. Both modes
   preserve aspect ratio and transparency. Bilinear uses one shared WebGL
   renderer with LINEAR texture filtering; if the GPU is unavailable or an
   image exceeds its texture limits, the default thumbnail remains visible
   and its tooltip explains the fallback. Bilinear and default can look
   similar, since the browser's default also commonly smooths images.

   Clicking an image brings it in front of other icons in that directory
   or on the desktop; desktop shortcuts remain below application windows.
   Size and scaling preferences persist per directory/file (and per desktop
   shortcut). The front-to-back order lasts until the view is rebuilt.
   Alt+double-click does not open the image. Ordinary double-click swaps the window's content area to
   a full-viewport image view (fills the directory window, not the whole
   app). Click "◀ Back" or press `Esc` to return to the listing.
4. **Windows-98-style internal windowing.** Directories open as their own
   panel inside the app's "desktop" — you can have as many open at once as
   you like. Each window has a titlebar (draggable), a location bar (type a
   path or a `vdir://` URI and hit Enter/Go), and can be resized from any
   edge or corner. Double-click the titlebar to maximize/restore; the `_`
   button "shades" the window (collapses it to just the titlebar) instead of
   using a taskbar. `Ctrl+L` or `Alt`/`Option`+`D` jumps straight to the
   active window's location bar (unshading it first if needed) and selects
   its contents. Real directories always show with a trailing separator
   (`/` on macOS/Linux, `\` on Windows) so you can just start typing a
   subfolder name right after it.

   **Window system menu:** click the small icon at the left of a titlebar,
   right-click the titlebar, or press **Alt+Q** for the active
   window. On macOS, **Command+Space** also opens it when delivered to the app.
   Alt+Space is left to the operating system.
   This is shared by folder and terminal windows. Use Up/Down and Enter to
   choose, or press a menu mnemonic: **R** Restore, **M** Move, **S** Size,
   **N** Minimize, **X** Maximize, **C** Close. **Alt+F4** closes the active
   internal window. Escape or clicking outside dismisses the menu.

   - **Move:** arrows move the window by 8 pixels; Ctrl+arrow moves by 1 pixel.
     Mouse motion can also move it without holding a button.
   - **Size:** the first arrow selects a border (Left/Right or Up/Down).
     Subsequent arrows on that axis move that border; an arrow on the other
     axis selects a corner so both axes can be resized. Ctrl+arrow makes
     1-pixel adjustments. With the mouse, reach a border to select it, then
     move the mouse to resize. Minimum window dimensions are respected.
   - **Enter or a left click** commits Move/Size. **Escape or a right click**
     cancels, restoring the original geometry and maximized/collapsed state.
     Switching away from the app cancels an unfinished operation as well.

   All commands remain enabled. Move/Size restore a maximized window to its
   normal bounds first; Size also opens a collapsed viewport. Restore opens
   a collapsed window or returns a maximized window to its normal size.
   Minimize keeps the existing titlebar-only collapse behavior. Double-clicking
   a collapsed titlebar restores its previous size instead of maximizing it. Repeating
   Maximize or Minimize keeps that state rather than toggling it. These are
   in-app emulations: they don't move the operating system's pointer or
   invoke Windows Snap layouts. Geometry changes preserve the existing
   content rather than reloading the directory.

   Reference behavior: [Microsoft Windows keyboard guide](https://ptacts.uspto.gov/ptacts/public-informations/petitions/1524761/download-documents?artifactId=sYHp6sNs2MHUPFkjFaJjc0ClYNZlOe3Y0d12cLRFBInH6l0BeKdZt7I)
   and [Windows keyboard shortcuts](https://support.microsoft.com/en-us/windows/keyboard-shortcuts-in-windows-dcc61a57-8ff0-cffe-9796-cb9706c75eec).
5. **Floating toolbar.** A small draggable toolbar (drag it by the `⠿`
   handle) always targets whichever window is currently active. The active
   window's titlebar is highlighted teal. Toolbar buttons:
   - **◀ / ▶** — step back/forward through that window's visited
     directories (mirrors the mouse side buttons below).
   - **Up** — go to the parent directory of the active window.
   - **View** — toggle the active window between detail and icon view.
   - **New Folder** — create a folder in the active window's directory.
   - **New Window** — open another window at your home directory.
6. **Navigation.** Each window keeps its own back/forward history (like a
   browser tab). `Backspace`, or `Alt`/`Option`+`Up Arrow`, goes up a
   directory. The mouse's side buttons (Back/Forward, if it has them) step
   through that window's history — same as the toolbar's ◀/▶.
   `Backspace`/`Delete` deliberately do **not** delete files; use
   `Cmd/Ctrl+Backspace` (matching macOS Finder's real Trash shortcut) to
   move the selection to the Trash instead.
7. **A real in-app terminal.** Right-click empty space in a window (or a
   folder icon, or the bare desktop) and pick **Terminal** — this opens an
   actual terminal emulator as its own window in the app's desktop, backed
   by a genuine pseudo-terminal (`node-pty`) running your default shell
   (`$SHELL` on macOS/Linux, `cmd.exe` on Windows) and rendered with
   [xterm.js](https://xtermjs.org) (the same engine VS Code's built-in
   terminal uses) — so interactive programs like `vim`, `less`, `top`, and
   colored output all work normally, not just simple non-interactive
   commands. Its own toolbar has:
   - **⚙ Settings** — font family (type any font name installed on your
     system, or pick from the suggestions), font size, text color,
     background color, and a cursor-blink toggle. One shared profile,
     applied live to every open terminal and remembered across restarts.
   - **Clear** — wipes the screen, like typing `clear`/`cls`.

   Other things it does without asking: selecting text copies it
   automatically; right-click pastes the clipboard; when the shell exits
   (you typed `exit`, or the process ended), it prints an exit message and
   the titlebar marks it `(exited)` rather than silently closing, so you
   don't lose output you were still reading. The **"New Terminal"** button
   on the floating toolbar (or the desktop's own right-click menu) opens
   one at your home directory. Separately, the original **Open Terminal
   Here**/**Open Command Prompt Here** item is still there too — that one
   launches your actual system Terminal/Command Prompt as its own native
   OS window, which is sometimes what you want instead. Not available
   inside virtual directories (there's no real directory to `cd` into).
8. **Desktop shortcuts.** Three ways to make one: hold `Alt`/`Option` while
   dropping a file onto the app's own desktop background (not inside any
   window); right-click a file or folder anywhere and choose **Create
   Desktop Shortcut**; or right-click the bare desktop itself and choose
   **Create Shortcut…**, which opens a small dialog to paste or type a
   path directly (surrounding `"` or `'` quotes, like you'd get from a
   "Copy as path" elsewhere, are stripped automatically). However it's
   made, a shortcut is a small colored-square alias, freely draggable,
   that double-click-opens the real file or folder. Persists across
   restarts; right-click one to remove it (the underlying file is
   untouched).
9. **Open With….** Right-click any file and pick **Open With…** to browse
    for an application (native file picker — on macOS this lets you select
    an actual `.app` bundle, matching Finder's own picker). That choice is
    remembered per extension: every `.png` (or whatever) opens with it from
    then on, including overriding the built-in image viewer if you'd rather
    a real image editor opened instead. It's a global preference, not
    per-file — right-click a different file of the same type and choose
    **Open With…** again to change it.
10. **Settings.** `File > Settings…` (`Cmd/Ctrl+,`) in the menu bar opens a
    panel for the app's own appearance: icon size, UI font size and family,
    titlebar color, and the desktop background — a solid color, or **Choose
    Image…** for an actual picture (scaled to cover, like a real wallpaper).
    Everything applies live to every open window and persists across
    restarts. Leaving the desktop color untouched keeps the original
    gradient rather than flattening it to a flat color — "Reset to
    Defaults" restores that too, not just a literal color value.
    Icon size accepts 16–3840 pixels. **Icon label background** changes the
    name box color; **Label opacity** adjusts its alpha from 0% (transparent)
    to 100% (opaque), without fading the text. A checkerboard preview shows
    both settings before saving. These preferences apply to folder icons and
    desktop shortcuts and persist across restarts. Selected labels retain
    their blue highlight. Changing only label appearance preserves folder
    viewports. Reset restores the original white background at 88% opacity.
    **Use file/folder icons** defaults off to preserve the existing color-block
    appearance. **Native size presets** set the default size to **16 px** or
    **32 px**; the minimum is already 16 px. Other sizes remain available but
    scale the native artwork. Per-file size overrides still take precedence.
    On high-DPI displays the best available OS image representation is used;
    CSS pixels and physical display pixels are not necessarily one-to-one.
    Baseline icon extraction uses Electron's built-in
    [app.getFileIcon](https://github.com/electron/electron/blob/main/docs/api/app.md#appgetfileiconpath-options),
    with no additional libraries. Windows also uses a persistent local
    PowerShell/.NET helper calling the Shell's icon image factory for larger
    artwork (requested sizes 16, 24, 32, 48, 64, 96, 128 and 256 px). It uses
    icon-only extraction, preserving alpha rather than substituting document
    previews. macOS uses its built-in JXA/AppKit support for sizes through
    1024 px; that platform helper has not been exercised on a Mac here.
    Linux retains all size/scale representations supplied by Electron.

    Each listed file preloads its complete size set, including offscreen
    entries. Resizing chooses the best cached image for its displayed size
    and display scale, without further OS lookups. Requests have bounded
    concurrency and caches evict whole families when over budget (64 MiB in
    the main process); changed file modification times invalidate old keys.
    If a platform helper is unavailable, Electron's smaller icons remain as
    a fallback. Very large icons can still look soft beyond the artwork the
    OS supplies. The folder SVG remains scalable at every size.
    Ctrl+wheel-down and restored sizes never go below 16 px, keeping a
    16×16 icon at least at its 100% logical size.
11. **Favorite images.** The image viewer's toolbar has a ☆ button — click it
   to star whatever you're looking at (it turns ★ and gold). Starred images
   show up in **Favorite Images**, a virtual directory just like Live Clock
   or Color Gallery, reachable via the viewer's "⭐ Favorites" button or by
   typing `vdir://favorites` into any location bar. Unlike the other
   built-in virtual directories, favorites point at your actual files —
   double-clicking one opens the genuine image, and next/prev/zoom/pixelated
   all work normally there too. It's still a read-only view though (no
   rename/trash/drag from inside it); un-favorite from the viewer's ★
   button instead. A favorite whose file has since been moved or deleted
   just quietly stops showing up, rather than erroring.
12. **Extra file-manager features included:**
   - Multi-select via `Cmd/Ctrl`-click, `Shift`-click, or a rubber-band
     marquee drag in empty space.
   - Right-click context menus (cut, copy, paste, rename, move to Trash,
     copy path, reveal in Finder, open terminal here, new folder, refresh,
     switch view) that actually close when you left-click elsewhere — including
     when that click lands on another file icon or the desktop, which
     previously could swallow the click before it reached the menu's own
     dismissal logic. Also closes on `Esc`.
   - Inline rename (`F2` or context menu), select all (`Cmd/Ctrl+A`), open
     (`Enter`).
   - Cut/copy/paste with `Cmd/Ctrl+X` / `Cmd/Ctrl+C` / `Cmd/Ctrl+V` between
     any two windows. Cut items dim in place until pasted.
   - Drag and drop between open windows — drag a file's colored square (or
     a detail-view row) from one window and drop it onto another to move
     it; hold `Ctrl` while dropping to copy instead. Dropping a file
     back onto the window it's already in repositions its icon instead of
     touching the filesystem. The drop preserves the cursor's exact grab
     point, matching the translucent drag preview even for resized icons;
     multi-selected icons keep their relative spacing. Repositioning updates
     icons in place, preserving the folder's viewport, selection, and stacking
     order instead of reloading the listing. This uses plain browser drag-and-drop rather
     than Electron's native `startDrag()` — the native version hands the
     whole gesture to the OS and never fires drop events back inside the
     app, which broke same-window rearranging; plain HTML5 DnD doesn't have
     that problem.
   - **Shift+drag** exports real files and folders to Explorer/Finder using
     native drag-and-drop. Ordinary dragging retains in-app positioning.
     Windows native drag supports move/copy (Ctrl requests copy); macOS uses
     Electron's native drag support, which offers copying. Drag files from
     Explorer/Finder directly into a folder window to move, or Ctrl-drop to copy.
   - Image viewer: `Right Arrow`/mouse-wheel-down goes to the next image in
     the directory, `Left Arrow`/mouse-wheel-up goes to the previous one
     (wraps around at the ends), `Esc` closes the preview. Hold `Ctrl` (or
     `Cmd`) and use the mouse wheel — or a trackpad pinch — to zoom from
     20% to 500%; a percentage readout shows in the preview's toolbar, and
     zoom resets to 100% each time you switch images. A "Smooth"/"Pixelated"
     button toggles nearest-neighbor scaling on and off (handy for pixel
     art) and stays as you set it while you browse.
   - Location bar autocomplete: start typing a path and press `Tab` to
     cycle forward through matching **directories** in that folder
     (`Shift+Tab` cycles backward).
   - A native app menu (`File > New Home Window`, `New Virtual Directories
     Window`, `Settings…`).
   - Status bar per window showing item/selection counts.

## Folder search

Click **S** to the right of a folder's **Go** button to open its linked Search
window, or press **Ctrl+F** or **Ctrl+E** (also while typing in the address
bar). These shortcuts focus/select the query in an existing Search GUI.
There is one search GUI per folder window; clicking S again brings it
forward. Enter a filename substring (case-insensitive; not a wildcard pattern)
and click Search or press Enter.

- **Search Recursively** searches the current folder and its descendants;
  unchecked searches only the current folder. Files and folders can match.
- With neither **Select** nor **Highlight** checked, a new read-only results
  window shows Name, **Parent Directory**, Kind, Size, Date Created, and Date
  Modified. Columns remain sortable and resizable; double-click opens an item.
  Right-click offers Open Parent Directory, and Refresh reruns that search.
- **Select** selects matching items currently listed in the originating folder.
- **Highlight** puts an aqua border around matching items in that folder, in
  icon or detail view. Both actions may be checked together. Recursive matches
  in child folders don't get added to the originating folder's listing.
- **File → Settings → Search highlight color** changes that border globally and
  persists across restarts. Highlights survive view changes but clear on folder
  navigation. Clear Highlights removes them explicitly; a new search with
  Highlight unchecked also clears earlier search borders.

Stop cancels a search. Navigating the source folder cancels pending work and
updates its Search window's scope; closing the folder closes its Search GUI.
Result windows remain independent snapshots. Unreadable subfolders are skipped
and reported. Search follows the app's existing hidden-dotfile policy, avoids
following real directory symlinks, and also supports virtual directories. Large
searches are bounded to 10,000 results/directories and two minutes; any truncation
or timeout is reported rather than presented as a complete search.

## Virtual directories ("scripted local pages")

Any `*.vdir.js` file dropped into `virtual-directories/` becomes a navigable
folder at `vdir://<id>`, generated by your code instead of the filesystem.
Scripts run in the Electron main process, so they have full Node.js access
(see `system-info.vdir.js` for an example using `os`).

Open `vdir://` in any location bar (or **File > New Virtual Directories
Window**) to see all installed scripts as folders.

### Script shape

```js
module.exports = {
  id: 'my-thing',        // becomes the path segment: vdir://my-thing
  label: 'My Thing',      // display name at the vdir:// root
  description: '...',     // optional, for your own documentation

  // Called every time the folder (or a subfolder of it) is opened.
  // `subpath` is whatever comes after the id, e.g. "sub/dir".
  list: async (subpath) => {
    return [
      {
        name: 'hello.txt',
        kind: 'file',            // 'file' | 'directory' | 'image'
        color: '#4fd1c5',        // optional — square color, hex
        size: 12,                // optional — display only
        modified: Date.now(),    // optional — epoch ms, display only
        created: Date.now(),     // optional — epoch ms, display only
        content: 'Hello world!', // shown in a text viewer on double-click
      },
      {
        name: 'a-generated-image.svg',
        kind: 'image',
        dataUrl: 'data:image/svg+xml;base64,...', // shown full-viewport
      },
      {
        name: 'a-real-photo.jpg',
        kind: 'image',
        realPath: '/Users/you/Pictures/photo.jpg', // points at an actual
        // file instead of a synthetic vdir:// address — the viewer opens
        // the genuine image (see favorites.vdir.js for a full example).
      },
      {
        name: 'nested',
        kind: 'directory', // navigating into it calls list('nested')
      },
    ];
  },
};
```

Four example scripts are included:

- `clock.vdir.js` — generates text files describing the current time.
- `colors.vdir.js` — generates a gallery of solid-color SVG "images" (plus a
  nested `pastel` subfolder), demonstrating generated images and nested
  virtual folders.
- `system-info.vdir.js` — exposes live OS/CPU/memory info as text files.
- `favorites.vdir.js` — lists whatever you've starred from the image
  viewer, demonstrating `realPath` (entries backed by actual files rather
  than generated content) and a script reading state that another part of
  the app writes.

Virtual entries are read-only (no rename/delete/new-folder/drag) even when
they use `realPath` and point at a genuine file — simple and safe, since a
virtual listing might reference the same file from several different
"folders". Un-favorite from the image viewer's ★ button rather than
through the favorites folder itself.

## Known simplifications

Given the scope of this build, a few things were deliberately kept simple:

- Dotfiles are hidden from listings.
- Window "minimize" shades the window in place rather than using a taskbar.
- Icons you haven't manually moved are auto-arranged into a grid slot based
  on their own position in the listing — moving one somewhere custom no
  longer shifts anything else. This doesn't try to avoid overlapping icons
  you've dragged into the same area, though, and a very different sort
  order (e.g. switching to sort by size) will still shuffle default slots
  around, since "default position" is tied to list order, not identity.
- Virtual (generated) entries aren't draggable, cuttable, or pasteable —
  they're read-only since there's no real file backing them. Terminal and
  desktop-shortcut actions are likewise unavailable for them (no real path).
- Name collisions on move/copy are resolved as "name copy 2.ext", "name
  copy 3.ext", etc., rather than Finder's exact naming scheme.
- Ordinary drag gestures use HTML5 for precise icon positioning; Shift+drag
  hands the gesture to the OS and supports multiple files and folders.
  Actual drops into Explorer/Finder still need a hands-on platform check.
- "Open With" and "Change Icon Color" are both per-*extension*, not
  per-file — there's no way to open just one particular `.txt` file
  differently from the rest, by design, matching how file-type
  associations normally work.
- Changing icon size in Settings changes the visual square size and the
  default grid slot spacing immediately, but icons that already have a
  manually-dragged (saved) position keep those exact pixel coordinates —
  they won't re-flow to a new spot just because the grid got bigger or
  smaller around them.
- Detail-view column widths reset each time you restart the app (not
  persisted to disk, unlike icon positions).
- "Date Created" reflects whatever the OS/filesystem reports as birthtime.
  Some Linux filesystems don't track true creation time and fall back to
  the same value as another timestamp — that's an OS-level limitation
  Finder and Explorer have too, not a bug here.
- Mouse-button Back/Forward and the toolbar's ◀/▶ were built and reviewed
  against the DOM's standard button-index convention (3 = back, 4 =
  forward) but couldn't be tested with a real mouse in this environment —
  worth confirming your mouse's side buttons actually report those codes.
- Desktop shortcuts render at a fixed z-index below every window, and their
  drag/reposition logic reuses the same lightweight mousedown-tracking
  pattern proven out in icon view, rather than the native-drag machinery
  that caused trouble for in-window dragging.
- Spatial arrow-key navigation (icon view) was unit-tested against the
  scoring algorithm directly — both a clean grid and a deliberately
  irregular layout (simulating freely-dragged icons) resolve correctly —
  but hasn't been exercised with a real keyboard in this environment.
- Favorites are matched by exact resolved file path. Renaming or moving a
  favorited file through the app breaks the link silently (it just stops
  appearing in Favorite Images, same as if it were deleted) rather than
  updating the stored path — re-favorite it afterward if that happens.
- The nearest-neighbor/smooth toggle persists for the life of a window's
  preview session rather than being remembered per-image or across restarts.
- Type-ahead selection was unit-tested directly against its buffer/cycle
  logic (multi-letter narrowing, same-letter cycling, the 800ms timeout
  reset, no-match handling all check out) but hasn't been tried with a
  real keyboard here.
- "Create Shortcut…"'s path dialog is a custom-built modal rather than the
  browser's `window.prompt()`, since Electron doesn't reliably support
  that in the renderer — it's plain HTML/CSS, so it should behave
  consistently, but (like everything interactive in this project) wasn't
  visually verified in this environment.
- The trailing separator in the location bar (and the Tab-autocomplete
  fix that goes with it) was written and logic-tested to handle Windows
  paths (`\`) correctly alongside `vdir://` URIs, but this was actually
  built and tested on a Mac, so the Windows-specific path came from
  reasoning plus isolated tests rather than a real Windows run — worth
  double-checking there first.
- **The terminal is the one feature in this project I couldn't meaningfully
  test end-to-end**, and it's worth being specific about why, and what I
  did verify instead. `node-pty` is a native module; compiling it requires
  fetching Node's headers from nodejs.org, which isn't reachable from the
  sandboxed environment this was built in — so I could never produce a
  working binary or run a real terminal session here, on top of not having
  a display to run Electron's GUI at all. What I *could* do, and did:
  installed `node-pty` with its native build skipped to read its actual
  compiled JS and TypeScript definitions, and confirmed the exact API
  shape (`pty.spawn(file, args, opts)`, `.onData()`, `.onExit()` firing
  `{exitCode, signal}`, `.write()`, `.resize()`, `.kill()`) — main.js's
  handlers are written to match that precisely. I then wrote a small mock
  matching that same surface and ran main.js's actual spawn/input/resize/
  kill/exit/cleanup logic against it: single-terminal lifecycle, a
  `vdir://` cwd correctly falling back to the home directory, explicit
  kill, multiple simultaneous terminals not cross-talking, `before-quit`
  cleanup actually killing every live process, and operations on an
  already-exited terminal being safe no-ops — all pass. Separately, I
  installed `@xterm/xterm` and `@xterm/addon-fit` for real, confirmed via
  static analysis of their UMD wrapper source (corroborated by their
  `require()` export shape) exactly what `window.Terminal` and
  `window.FitAddon` resolve to in a plain `<script>` tag context, and
  vendored the real compiled bundles rather than approximating them.
  So: the architecture is right, the main-process logic is genuinely
  tested, and the browser-global wiring is verified by more than
  guesswork — but the actual native compile, and the full spawn-a-shell,
  type-into-xterm.js, see-it-echo-back loop, still needs a real run on
  your machine to be certain of. If it doesn't work, the in-app error
  message (or this section) should at least tell you why.

## Media Player and desktop labels

Open **File → Media Player**, or the Media Player desktop icon. The original
Winamp 3-inspired interface has a pale-blue LCD, teal luminous text, a playlist,
and seven transport controls: previous, next, stop, play/pause, record, reverse,
and loop mode. Loop cycles between stop after playlist, repeat one track, and
repeat the whole playlist. Reverse plays the actual audio backwards; it decodes
that track into memory (limited to 128 MB files and 20-minute tracks).

Drag audio files from folder windows or the OS into the playlist, or use its
Player menu to add files. Double-click/Enter plays a selected track; Delete
removes it from the playlist only. Player menu also exports UTF-8 M3U playlists
with absolute file paths. Playback uses Electron's codecs (including common
MP3, WAV, FLAC, Ogg/Opus and supported AAC/M4A files); unsupported encodings
report an error. The playlist is session-local unless exported.

Expand **Recording · input and format** to select an input, mono/stereo, WAV
16/24-bit, output sample rate (44.1/48/96/192/384 kHz), or Ogg Opus quality
(64–320 kb/s). Actual input rate is reported when recording. Device/driver and
OS permissions determine input capabilities; WAV output may be resampled.
A higher output sample rate or bit depth does not create missing input detail.
Opus output runs at 48 kHz. Encoding uses built-in WebCodecs with Ogg framing;
PCM capture runs in an AudioWorklet and streams to disk without accumulating
an entire recording in memory. No codec dependency was added.

Record starts immediately after microphone permission, without a naming prompt.
Stop or Record again finishes it and offers a filename. A safe automatic copy
is retained under **Music/EFM Recordings/MyRecording000.wav** (or `.ogg`),
advancing the number without overwriting existing recordings. Cancelling the
save dialog keeps that file; choosing another path saves an additional copy.
Closing the player or app finishes the recording under its automatic name.
WAV headers are updated during capture so interrupted files can be recovered.
The standard RIFF size limit is approximately 4 GB per recording.

Desktop label font sizes are defined at a 48 px icon size and scale in direct
proportion to the icon. Appearance adds X/Y offsets in screen pixels, with a
spring-centered joystick: drag and hold to nudge at up to 12 px/second, or hold
Shift for up to 2 px/second. Arrow keys nudge by 1 px (Shift: 0.1 px); numeric
fields also accept precise values. Offsets are independent of the anchor and
persist with that icon's appearance.

Tests include synthetic microphone recordings at multiple rates, real decoding
of 16/24-bit WAV and Ogg output, cancelled filename dialogs, reverse playback,
loop modes, M3U serialization, proportional label zoom and precise offsets.
Physical recording devices and macOS still require platform-specific testing.

## File history, image windows, drives, and HTML backgrounds

At the bottom of Settings' left column, **History filetypes** accepts comma-separated
extensions such as `png, .jpg, txt`. Matching is case-insensitive; blank disables new
entries without deleting existing history. Open `vdir://history` through the location
bar or **File → New Virtual Directories Window → File Activity History**. Its detail
columns are Action, Path, Path2, and Time. Opens have an empty Path2; moves/renames
store full old and new paths. Matching files inside moved/renamed folders are included.
Copies and failed operations are not logged. History covers EFM-managed operations,
external-program launches, image viewing and player track starts, not activity performed
independently by another application. A successful launch means the OS/program accepted
the request, not that the external program finished reading the file. History is stored
locally in `activity-history.json` alongside EFM's other user-data files.

Images open in separate internal viewer windows, preserving the source folder's
selection and scroll position. The viewer retains zoom, favorites and sibling-image
navigation; Escape or its Back button closes it. Saved Open With associations still
take precedence. Up from a filesystem root opens `vdir://drives`: available drive letters
on Windows and filesystem/mounted volumes on macOS (which does not use drive letters).

The Background control starts anchored at the lower left. Click to cycle:

1. View-only HTML background; normal desktop input.
2. Interactive HTML beneath visible desktop icons and windows.
3. Interactive HTML filling the app viewport, with other desktop content hidden.

The control always remains visible. Right-click it to select a page, import an HTML
file, use the ordinary desktop color/image, open Appearance, or restore its lower-left
anchor. Ctrl+wheel resizes it; dragging saves its position and keeps it within a resized
viewport. Appearance supports custom images and labels. Each launch starts in view-only
mode. The selected page and control appearance/position persist.

Pages live in the project's `Backgrounds` directory. With no saved selection, filenames
use ordinal order (ASCII digits, uppercase letters, then lowercase letters, not natural
numeric sorting). `000-Desktop.html` provides a simple clock background. Imports copy
the HTML file without overwriting another page; companion assets are not copied, so use
self-contained HTML or place its required assets in Backgrounds as well. The embedded
page can run JavaScript and forms but is sandboxed without EFM/Node access, parent-window
access, popups, or camera/microphone/clipboard permissions. Fullscreen means the EFM app
viewport; the control remains available to exit this mode.

Windows integration checks cover history, root-drive listing, image-window isolation,
background importing, input modes, and sandboxed script execution. Mounted-volume
discovery on macOS still requires testing on a Mac.

## Address suggestions, metadata view, and live search

The location bar shows matching folders while typing. Tab/Down cycle forward;
Shift+Tab/Up cycle backward, with wrapping. Ctrl+L and Alt+D select the entire
path even when the field already has focus. Escape dismisses suggestions and
focuses the folder view. Enter/Go opens an exact directory, launches an exact
file using its saved Open With association (otherwise the OS default), or opens
the first alphabetically matching folder when the final path component is
incomplete. Missing or inaccessible locations leave the current view intact.

Desktop Appearance includes a Displayed name field. It changes only the shortcut
label, not its target filename. A blank value restores the default name.

Favorites image and file/folder icons can be repositioned within their virtual
folder; positions use unique entry identities, including duplicate filenames.
Cross-folder drops into virtual folders remain disabled.

Open **File → New Virtual Directories Window**, then **File Notes, Numbers and Hashes**, or enter
`vdir://metadata`, to inspect stored notes, # values, hashes and rename history.
This uses the existing `entry-metadata.json` in Electron's user-data directory.
It starts in detail view with Parent Directory and all normal columns, and can
switch to icons. Unavailable files are omitted without deleting their records;
hashes invalidated by file changes are not shown. Notes and # remain editable.

Search updates 250 ms after typing or changing options. Each search cancels its
predecessor, reuses one results window, and streams partial results while keeping
typing focus. An indeterminate progress bar and folder/match counts indicate work
without inventing a percentage for an unknown directory tree. Stop cancels the
current search and retains displayed results; clearing the query clears results.

## Player controls, native clipboard, and folder layouts

Player-only chrome and surrounding panels use #233040. Recording device and
format dropdowns use #233040 with #AEDAE5 text. Player menu → Help opens a
nonmodal reference for the transport, playlist, speed, and display controls.

Hold Ctrl while dragging the speed slider for 20× finer movement; Ctrl can be
pressed or released during the gesture. Two slider clicks within 300 ms reset
speed to 1.00×. Click the numeric value to enter a positive speed, Enter to apply,
or Escape to cancel. Typed values may exceed the slider's 3× maximum, subject to
Chromium's playback-rate limits; rejected values leave the previous rate intact.
Comma and period lower/raise speed by one semitone (a factor of 2^(1/12)).

The Output selector beneath Recording routes normal and reverse playback through
the same AudioContext output. It remains usable during recording and does not
enable microphone monitoring. Disconnected outputs fall back to the default;
failed selections retain the previous device. Device visibility/names depend on
OS/browser permissions. Chromium's device enumeration does not report per-device
MME/DirectSound/WASAPI backend names, so the UI does not guess those labels or
offer unsupported driver-mode switches. Output routing was tested with the default
device and simulated device changes/failures; switching physical output hardware
and macOS behavior still need platform testing.

- Drag the bottom border of the player LCD to resize it. The display height
  persists; spectrum height sets its minimum required space.
- Drag playlist rows to reorder. Hold Ctrl on drop to insert a duplicate entry
  (no filesystem copy). The playing track continues uninterrupted as its row moves.
- The speed slider beside Recording ranges from 0.25× to 3×. Pitch shifts with
  speed, including reverse playback; no time-stretch/pitch correction is used.
- Player menu → Settings controls 5–24 spectrum bands, maximum bar height,
  bottom/top gradient colors, and single-color mode. The default is the previous
  muted blue LCD-bar color. Analysis uses real playback or recording audio.
  Bands include DC and then logarithmic frequencies through Nyquist (half the
  sample rate); PCM cannot represent frequencies above this limit.
- With the player active, Z/X/C/V/B/N/M activate previous/next/stop/play-pause/
  record/reverse/loop. These shortcuts do not intercept typing in fields.

File copy/cut/paste now reads and writes the native OS file clipboard. Windows
uses CF_HDROP plus Preferred DropEffect, with multiple files and folders. A cut
marks intent only: nothing is removed until a transfer succeeds. Successful
items are consumed, failed items remain available for retry, and clipboard
sequence checks prevent overwriting a newer clipboard. External drops are
acknowledged to their source as copies while EFM performs any requested move
itself, preventing a source application from deleting files while the async
transfer is still in progress. EFM's existing collision handling and creation-date
preservation apply to transfers it performs. Native transfers performed by
Explorer/Finder follow that program's timestamp/metadata behavior.

On macOS, Finder file URLs and filename lists are supported. Finder uses
Command+C followed by Command+Option+V for a move; it does not implement Windows
cut-then-regular-paste semantics. EFM's own Cut is recognized when pasted back
into EFM. Linux reads common GNOME/KDE file lists and publishes GNOME copied-files
format; this and macOS need platform testing. Only Windows clipboard behavior
has been exercised here. Clipboard tests save and restore the existing clipboard.

Right-click a folder window's background in icon view:
- **Offset Rows** offsets alternating rows by half the normal horizontal spacing.
- **Don't Reflow** freezes automatic positions across resizes and reopening.
- **Realign** puts every icon, including manually moved ones, onto the current
  grid, preserving individual icon sizes and thumbnail scaling.

These options are saved per directory. Toggling Offset Rows changes automatic
placements; manually positioned icons stay put until Realign. Favorite borders
now use an independent overlay so native icons and image thumbnails cannot hide
that configurable outline.

Windows native drag-out uses a small dedicated STA helper compiled from
`lib/windowsFileDrag.cs` with the Windows .NET Framework compiler, cached under
userData/native-helpers. It offers copy/move effects and never performs a second
source deletion after the drop target finishes. Release Shift after starting
the gesture, then hold Ctrl to request copy (Ctrl+Shift is the shell's link
modifier). Tests validate the helper's file-list and cancellation contracts;
a full live drag into Explorer/Finder remains a manual platform check.

## HTML background exports

Background pages can download generated WAV, MIDI (.mid/.midi), and other files

filename; WAV and MIDI exports get matching file filters. Cancelling leaves the
